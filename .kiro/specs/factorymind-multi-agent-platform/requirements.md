# Requirements Document

## Introduction

FactoryMind is a hierarchical multi-agent manufacturing intelligence platform built on AWS Bedrock AgentCore. The system processes real-time sensor data from 50 machines across 3 production lines at the Chennai Plant (PLANT-001), providing predictive maintenance, quality inspection, sustainability monitoring, and digital twin synchronization. A Brain Agent (LangGraph orchestrator) delegates to 6 Manager Agents, each managing specialized Worker Agents, with strict SLAs ranging from <10ms (edge inference) to <5s (sustainability analysis).

## Glossary

- **Brain_Agent**: The top-level LangGraph orchestrator that assesses alert severity, queries machine history, delegates to Manager Agents, and synthesizes unified recommendations.
- **IoT_Ingestion_Manager**: The agent responsible for processing real-time sensor data batches from Kinesis, validating readings, detecting anomalies, and routing data to storage.
- **Quality_Vision_Manager**: The agent that orchestrates the visual inspection pipeline using YOLOv8 and Rekognition fallback to classify product defects.
- **Predictive_Maintenance_Manager**: The agent that predicts machine failures using LSTM and Lookout for Equipment with consensus-based CRITICAL classification.
- **Sustainability_Manager**: The agent that monitors energy consumption, calculates sustainability KPIs, detects waste, and generates AI-powered optimization recommendations.
- **Digital_Twin_Manager**: The agent that maintains the real-time digital representation of the plant, synchronizing state across TwinMaker, Redis, and AppSync.
- **Edge_AI_Manager**: The agent that provides sub-10ms inference at the edge using ONNX Runtime, classifying sensor readings locally and escalating anomalies asynchronously.
- **EventBridge_Bus**: The Amazon EventBridge event bus (factorymind-bus) used for all inter-agent communication.
- **Sensor_Reading**: A single data point from a machine sensor containing temperature, vibration, pressure, RPM, and power values.
- **Work_Order**: A maintenance task generated by the Predictive_Maintenance_Manager when failure probability exceeds thresholds.
- **Consensus_Rule**: The requirement that both LSTM and Lookout for Equipment models must agree before a CRITICAL severity classification is assigned.
- **Sliding_Window**: The last 10 sensor readings maintained in Redis for Edge AI inference context.
- **Health_Score**: A normalized value between 0.0 and 1.0 representing the operational health of a machine.

## Requirements

### Requirement 1: Brain Agent Orchestration

**User Story:** As a plant operations manager, I want a central intelligence agent that assesses alert severity and coordinates specialized agents, so that manufacturing issues are handled by the right domain experts with appropriate urgency.

#### Acceptance Criteria

1. WHEN the Brain_Agent receives an alert event from EventBridge_Bus, THE Brain_Agent SHALL assess the severity by analyzing raw sensor values within 2 seconds
2. WHEN the Brain_Agent assesses severity as CRITICAL, THE Brain_Agent SHALL delegate to the Predictive_Maintenance_Manager, the Digital_Twin_Manager, and flag the decision for human escalation
3. WHEN the Brain_Agent assesses severity as HIGH, THE Brain_Agent SHALL delegate to the relevant domain manager and the Digital_Twin_Manager
4. WHEN the Brain_Agent assesses severity as MEDIUM, THE Brain_Agent SHALL delegate to the relevant domain manager only
5. WHEN the Brain_Agent assesses severity as LOW, THE Brain_Agent SHALL log the event to CloudWatch without delegating to any manager
6. WHEN the Brain_Agent delegates to multiple managers, THE Brain_Agent SHALL invoke them in parallel and wait for all results before synthesizing a recommendation
7. WHEN all delegated managers return results, THE Brain_Agent SHALL synthesize a unified recommendation and publish a BrainDecision event to EventBridge_Bus
8. WHEN the Brain_Agent completes processing, THE Brain_Agent SHALL include the processing_time_ms in the output and the value SHALL be less than 2000

### Requirement 2: IoT Data Ingestion and Anomaly Detection

**User Story:** As a data engineer, I want real-time sensor data validated, stored, and monitored for anomalies, so that downstream agents receive clean data and are alerted to abnormal conditions immediately.

#### Acceptance Criteria

1. WHEN the IoT_Ingestion_Manager receives a Kinesis batch of up to 100 sensor records, THE IoT_Ingestion_Manager SHALL validate each Sensor_Reading and process the batch within 500 milliseconds
2. WHEN a Sensor_Reading has a timestamp older than 60 seconds, THE IoT_Ingestion_Manager SHALL reject that reading and increment the records_rejected count
3. WHEN a Sensor_Reading has a temperature value outside the range 0 to 200 degrees Celsius, THE IoT_Ingestion_Manager SHALL reject that reading as an outlier
4. WHEN a Sensor_Reading has a vibration value outside the range 0 to 500 Hz, THE IoT_Ingestion_Manager SHALL reject that reading as an outlier
5. WHEN a Sensor_Reading has a pressure value outside the range 0 to 50 bar, THE IoT_Ingestion_Manager SHALL reject that reading as an outlier
6. WHEN a Sensor_Reading has an RPM value outside the range 0 to 10000, THE IoT_Ingestion_Manager SHALL reject that reading as an outlier
7. WHEN a Sensor_Reading has a power value outside the range 0 to 100 kW, THE IoT_Ingestion_Manager SHALL reject that reading as an outlier
8. WHEN a Sensor_Reading passes validation, THE IoT_Ingestion_Manager SHALL write the reading to the Timestream SensorReadings table and update the DynamoDB FactoryMind_MachineState table
9. WHEN a validated Sensor_Reading exceeds configured anomaly thresholds, THE IoT_Ingestion_Manager SHALL publish an AnomalyDetected event to EventBridge_Bus with the anomaly_score between 0.0 and 1.0
10. THE IoT_Ingestion_Manager SHALL produce an IngestionOutput containing records_processed, records_rejected, and anomalies_detected counts that sum correctly relative to the input batch size

### Requirement 3: Quality Vision Inspection

**User Story:** As a quality control engineer, I want automated visual inspection of products using AI models, so that defects are detected consistently and production quality is maintained without manual inspection bottlenecks.

#### Acceptance Criteria

1. WHEN a product image is uploaded to the factorymind-product-images S3 bucket, THE Quality_Vision_Manager SHALL initiate the inspection pipeline within 3 seconds
2. WHEN the Quality_Vision_Manager receives an image, THE Quality_Vision_Manager SHALL preprocess the image by resizing and normalizing it before model inference
3. WHEN the YOLOv8 model returns detections with confidence greater than or equal to 0.75, THE Quality_Vision_Manager SHALL accept the YOLOv8 result as the primary detection
4. WHEN the YOLOv8 model returns detections with confidence less than 0.75, THE Quality_Vision_Manager SHALL invoke Rekognition as a fallback detector
5. WHEN defects are detected, THE Quality_Vision_Manager SHALL classify each defect as one of SCRATCH, DENT, CRACK, DISCOLORATION, MISALIGNMENT, or NO_DEFECT
6. WHEN the inspection is complete, THE Quality_Vision_Manager SHALL produce a QualityInspectionOutput with a verdict of PASS, FAIL, or REVIEW
7. WHEN the inspection is complete, THE Quality_Vision_Manager SHALL record the result to the FactoryMind_QualityResults DynamoDB table and publish an event to EventBridge_Bus
8. WHEN the batch defect rate exceeds the configured threshold for the product type, THE Quality_Vision_Manager SHALL set threshold_exceeded to true in the output

### Requirement 4: Predictive Maintenance with Consensus

**User Story:** As a maintenance planner, I want AI-driven failure predictions that require model consensus for critical alerts, so that I can schedule preventive maintenance with high confidence and avoid false alarms on critical equipment.

#### Acceptance Criteria

1. WHEN the Predictive_Maintenance_Manager receives an alert, THE Predictive_Maintenance_Manager SHALL query the 72-hour rolling sensor window from Timestream for the affected machine
2. WHEN sensor history is retrieved, THE Predictive_Maintenance_Manager SHALL invoke both the LSTM SageMaker endpoint and Lookout for Equipment for independent predictions
3. WHEN both the LSTM model and Lookout for Equipment classify the alert as CRITICAL, THE Predictive_Maintenance_Manager SHALL set consensus_reached to true and assign final_severity as CRITICAL
4. WHEN only one model classifies the alert as CRITICAL, THE Predictive_Maintenance_Manager SHALL set consensus_reached to false and assign final_severity as HIGH
5. WHEN the final_severity is CRITICAL or HIGH, THE Predictive_Maintenance_Manager SHALL generate a Work_Order with a unique work_order_id, recommended_action, estimated_downtime_hours, and parts_required
6. WHEN a Work_Order is generated, THE Predictive_Maintenance_Manager SHALL queue it to the factorymind-workorder-queue SQS queue
7. WHEN a Work_Order has priority CRITICAL, THE Predictive_Maintenance_Manager SHALL set the predicted_by field to "consensus"
8. THE Predictive_Maintenance_Manager SHALL complete processing within 3 seconds and include processing_time_ms in the output

### Requirement 5: Sustainability Monitoring and Reporting

**User Story:** As a sustainability officer, I want real-time energy monitoring with carbon footprint calculations and AI-generated optimization recommendations, so that I can reduce the plant's environmental impact and energy costs.

#### Acceptance Criteria

1. WHEN the Sustainability_Manager performs real-time analysis, THE Sustainability_Manager SHALL calculate energy deviation percentage by comparing current consumption against baselines stored in FactoryMind_EnergyBaselines
2. WHEN calculating carbon footprint, THE Sustainability_Manager SHALL use the conversion factor of 0.82 kg CO2 per kWh for the India grid
3. WHEN calculating energy cost, THE Sustainability_Manager SHALL use the rate of Rs 7.50 per kWh
4. WHEN the Sustainability_Manager computes KPIs, THE Sustainability_Manager SHALL produce energy_efficiency (0.0 to 1.0), carbon_footprint_kg, waste_index (0.0 to 1.0), and overall_score (0 to 100)
5. WHEN generating optimization recommendations, THE Sustainability_Manager SHALL invoke Bedrock Claude 3.5 with context from Bedrock Knowledge Bases containing industry benchmarks
6. WHEN a weekly report is due, THE Sustainability_Manager SHALL generate a report and send it via Amazon SES
7. THE Sustainability_Manager SHALL complete processing within 5 seconds and include processing_time_ms in the output

### Requirement 6: Digital Twin Synchronization

**User Story:** As a plant floor supervisor, I want a real-time digital representation of all machines visible on a dashboard, so that I can monitor plant status at a glance and respond quickly to state changes.

#### Acceptance Criteria

1. WHEN the Digital_Twin_Manager receives a state update, THE Digital_Twin_Manager SHALL update the Redis cache with key pattern twin:state:{plant_id}:{machine_id} and TTL of 300 seconds
2. WHEN the Digital_Twin_Manager receives a state update, THE Digital_Twin_Manager SHALL persist the state to the FactoryMind_TwinState DynamoDB table
3. WHEN the Digital_Twin_Manager receives a state update, THE Digital_Twin_Manager SHALL synchronize the state to the IoT TwinMaker workspace
4. WHEN the Digital_Twin_Manager receives a state update, THE Digital_Twin_Manager SHALL publish the state change via AppSync updateMachineState mutation for real-time dashboard subscriptions
5. WHEN the state update has severity CRITICAL, THE Digital_Twin_Manager SHALL take a historical snapshot and store it in the factorymind-twin-snapshots S3 bucket
6. WHEN the Redis cache and DynamoDB state diverge, THE Digital_Twin_Manager SHALL reconcile by treating DynamoDB as the source of truth
7. THE Digital_Twin_Manager SHALL complete state synchronization within 500 milliseconds and include processing_time_ms in the output

### Requirement 7: Edge AI Real-Time Inference

**User Story:** As a production line operator, I want immediate local classification of sensor anomalies without cloud latency, so that critical machine issues are flagged in real-time at the point of operation.

#### Acceptance Criteria

1. WHEN the Edge_AI_Manager receives a sensor reading via IoT Core rule, THE Edge_AI_Manager SHALL retrieve the Sliding_Window of last 10 readings from Redis for that machine
2. WHEN performing inference, THE Edge_AI_Manager SHALL execute the ONNX model and complete inference within 10 milliseconds
3. WHEN inference is complete, THE Edge_AI_Manager SHALL classify the reading as NORMAL, WARNING, or ANOMALY
4. WHEN the classification is NORMAL, THE Edge_AI_Manager SHALL update the Sliding_Window in Redis and log the result to CloudWatch without escalation
5. WHEN the classification is ANOMALY, THE Edge_AI_Manager SHALL publish an escalation event to EventBridge_Bus asynchronously using fire-and-forget pattern
6. THE Edge_AI_Manager SHALL NOT wait for any cloud response after publishing an escalation event
7. THE Edge_AI_Manager SHALL NOT retry failed escalation attempts
8. WHEN inference is complete, THE Edge_AI_Manager SHALL record the result to the FactoryMind_EdgeResults DynamoDB table with inference_time_ms

### Requirement 8: Sensor Data Validation

**User Story:** As a data quality analyst, I want all sensor readings validated against physical constraints before processing, so that invalid or corrupted data does not propagate through the system and cause false alerts.

#### Acceptance Criteria

1. THE IoT_Ingestion_Manager SHALL validate that machine_id matches the pattern MCH-\d{3} for all incoming Sensor_Readings
2. THE IoT_Ingestion_Manager SHALL validate that production_line is one of LINE-A, LINE-B, or LINE-C
3. WHEN a Sensor_Reading contains a value outside the valid physical range for its sensor type, THE IoT_Ingestion_Manager SHALL reject the entire reading
4. WHEN a Sensor_Reading is rejected, THE IoT_Ingestion_Manager SHALL increment the records_rejected counter and exclude the reading from downstream processing
5. THE IoT_Ingestion_Manager SHALL ensure that records_processed plus records_rejected equals the total number of records in the input batch

### Requirement 9: Work Order Lifecycle Management

**User Story:** As a maintenance technician, I want work orders with clear priority, actions, and parts lists generated automatically from predictions, so that I can prepare for and execute maintenance efficiently.

#### Acceptance Criteria

1. WHEN a Work_Order is created, THE Predictive_Maintenance_Manager SHALL assign a unique sequential work_order_id with prefix WO-
2. WHEN a Work_Order is created, THE Predictive_Maintenance_Manager SHALL set estimated_downtime_hours to a positive value
3. WHEN a Work_Order has priority CRITICAL, THE Predictive_Maintenance_Manager SHALL ensure the predicted_by field is set to "consensus"
4. WHEN a Work_Order is in OPEN status, THE Work_Order scheduled_date SHALL be in the future
5. THE Work_Order status SHALL only transition through valid paths: OPEN to IN_PROGRESS, IN_PROGRESS to COMPLETED, or OPEN to CANCELLED

### Requirement 10: Machine State Management

**User Story:** As a plant monitoring system, I want accurate real-time machine state tracked and accessible, so that all agents can make decisions based on current operational context.

#### Acceptance Criteria

1. THE FactoryMind_MachineState record SHALL maintain a Health_Score between 0.0 and 1.0 for each machine
2. WHEN a machine status changes, THE system SHALL only allow valid transitions: RUNNING to IDLE, IDLE to RUNNING, any status to MAINTENANCE, and any status to FAULT
3. WHEN the IoT_Ingestion_Manager writes a validated Sensor_Reading, THE IoT_Ingestion_Manager SHALL update the corresponding machine state record with the latest sensor values and timestamp
4. WHEN a machine is in RUNNING or IDLE status, THE system SHALL flag the machine state as potentially stale if last_reading_timestamp exceeds 60 seconds from current time

### Requirement 11: Inter-Agent Communication

**User Story:** As a system architect, I want all agent communication to flow through a centralized event bus with structured events, so that the system is decoupled, observable, and extensible.

#### Acceptance Criteria

1. THE Brain_Agent SHALL publish all decisions to EventBridge_Bus with source pattern factorymind.brain.decision
2. WHEN the IoT_Ingestion_Manager detects an anomaly, THE IoT_Ingestion_Manager SHALL publish an AnomalyDetected event to EventBridge_Bus containing machine_id, alert_type, severity, anomaly_score, and timestamp
3. WHEN the Edge_AI_Manager classifies a reading as ANOMALY, THE Edge_AI_Manager SHALL publish an escalation event to EventBridge_Bus for the Brain_Agent to process
4. WHEN any Manager Agent completes processing, THE Manager Agent SHALL include a unique ID with the appropriate prefix (BRN-, ING-, QCR-, PRD-, SUSR-, TWNR-, EDGR-) in the output

### Requirement 12: Performance SLA Compliance

**User Story:** As a platform reliability engineer, I want each agent to meet its defined latency SLA, so that the manufacturing intelligence system provides timely responses appropriate to each domain's urgency.

#### Acceptance Criteria

1. THE Edge_AI_Manager SHALL complete inference processing with inference_time_ms less than 10
2. THE IoT_Ingestion_Manager SHALL complete batch processing with processing_time_ms less than 500
3. THE Digital_Twin_Manager SHALL complete state synchronization with processing_time_ms less than 500
4. THE Quality_Vision_Manager SHALL complete the full inspection pipeline with processing_time_ms less than 3000
5. THE Predictive_Maintenance_Manager SHALL complete prediction analysis with processing_time_ms less than 3000
6. THE Sustainability_Manager SHALL complete analysis with processing_time_ms less than 5000
7. THE Brain_Agent SHALL complete the full delegation chain with processing_time_ms less than 2000
